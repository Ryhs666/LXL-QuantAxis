# ADR-0001：V2.0 采用模块化单体

- 状态：Accepted
- 日期：2026-08-03
- 决策负责人：LXL-QuantAxis Architecture
- 适用范围：LXL-QuantAxis V2.0

## 背景

当前系统是一个多入口 Python 单体。CLI、Tkinter、新旧 Flask Web 分别编排数据、策略、回测、AI 和持久化；业务模块可直接访问 CSV、SQLite、JSON 和外部 Provider。现阶段的主要问题是模块边界、交易时钟、风险闸门、数据血缘和测试门禁，不是独立部署能力。

立即拆成微服务会同时引入服务发现、网络故障、分布式追踪、消息一致性、部署编排和跨服务测试成本。在领域边界尚未稳定前，这些成本会放大现有问题。

## 决策

V2.0 首先采用模块化单体：

1. 在单一 Python 发布单元内建立 `core`、`data`、`research`、`factor`、`strategy`、`backtest`、`portfolio`、`risk`、`execution`、`ai`、`memory`、`api` 和 `dashboard` 边界。
2. 领域模块不依赖 Flask、SQLAlchemy、AkShare 或具体 LLM SDK。
3. 外部系统通过 Port/Adapter 接入；跨模块通过公开 Contract、Application Service 或 Domain Event 交互。
4. 禁止 UI 跨过 Application Service 直接访问其他模块的数据库表。
5. 现有入口通过兼容适配器逐步迁移，旧功能在迁移期保持可运行。
6. 不以目录移动代替边界建设；先建立契约和特征测试，再迁移实现。

## 结果

### 正面影响

- 保留单进程调试、部署和本地研究的简单性。
- 可在不引入分布式故障的前提下强制依赖方向。
- 旧入口可渐进迁移，降低一次性重写风险。
- 稳定模块未来可按真实容量和团队边界独立拆分。

### 代价

- 需要持续执行模块依赖规则，避免再次退化为无边界单体。
- 长任务仍需进程内队列或独立 Worker Adapter，但不能直接共享可变全局状态。
- 单一部署单元的扩缩容粒度较粗。

## 约束

- 新代码必须放在明确模块内，并只通过公开接口跨模块调用。
- 兼容层只做协议转换，不能承载新业务逻辑。
- 数据库表按模块归属；禁止跨模块直接写表。
- 核心领域对象不得导入 Web 或 ORM 类型。

## 重新评估触发条件

满足下列任一条件时评估拆分，而不是自动拆分：

- 数据采集和研究任务需要与交互 API 独立扩缩容。
- 某模块有独立团队、发布节奏和 SLO。
- 单体发布或故障域成为有数据证明的瓶颈。
- 安全或许可要求强制物理隔离。

## 备选方案

- 保持现有单体：拒绝。无法解决边界和可信研究问题。
- 立即微服务化：拒绝。当前收益不足以覆盖分布式复杂度。
- 全量重写：拒绝。会丢失已有数据契约、策略/因子资产和产品经验。
